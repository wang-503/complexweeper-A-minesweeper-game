# 复扫雷 Complexweeper · 安卓版

这是 Windows 原生版（Zig + Win32）的安卓移植。规则、素材、界面观感都与 Windows 版一致，
装到手机上是一个**没有任何 Java 代码**的纯原生应用。

## 快速上手

```powershell
# 构建（第一次会下工具链，约 1.1 GB，缓存在 android/.android-tools/）
powershell -ExecutionPolicy Bypass -File android/build.ps1

# 装到手机上
adb install -r "android/build/复扫雷-android-<版本>.apk"
```

产物：`android/build/复扫雷-android-<版本>.apk`（约 160 KB，仅 `arm64-v8a`）。

## 操作方式（触屏）

电脑版是「左键翻开 / 右键循环插旗 / 左右键同时按展开」。有四种旗加上无旗共五种状态，
长按一次只走一步太慢，所以安卓版把操作反过来了：

| 手势 | 效果 |
| --- | --- |
| **单指点按** | 循环插旗：空 → +1 → −1 → +i → −i → 空 |
| **单指长按** | 翻开（按住期间会先把那一格画成翻开的空白，和电脑版一样） |
| **双击** | 展开（等价电脑版的左右键同时点 / 中键，判据不通过时什么都不做） |
| **拖动棋盘** | 平移视野，看棋盘以外的那部分（高级盘一屏放不下） |
| **拖动滚动条** | 右侧竖条 / 下方横条，拖滑块也能平移视野（厚度 = 一个格子，紧贴棋盘无缝隙） |
| **点人脸** | 重开一局 |

几个细节：

- 点按要等 **250 ms** 才真正插旗 —— 这是留给「双击」判定的窗口。
- 长按阈值 **350 ms**，双击窗口 **450 ms**，都在 `src/ui.h` 顶部的 `UI_*_MS` 常量里。
- 已插旗的格子长按无效（旗子保护它，和电脑版一致）。
- 已翻开的数字格长按也能展开，作用同双击。
- **拖动阈值 2px**（`UI_PAN_SLOP_PX`）：它只管区分"按住不动"和"开始拖"。
  小于它时认为手指还按在原处（长按 / 点按照常可用，画面不动）；
  一到阈值立刻切成拖动，画面**从按下点一比一跟手**（不丢位移、不跳）。
  2px ≈ 0.18mm，最慢的拖动（50px/s）也只要 40ms 就进入跟手。
  拖动只能从棋盘区起手，在侧栏或菜单栏上滑不会带着棋盘走。
- 拖动**精确到像素、不吸附到整格**：拖多少走多少，松手时画面**一点都不跳**。
  代价是屏幕左右边缘会出现**不完整的格子**（这是刻意的，网格更连续、也更像在
  "滑动一块大棋盘"）。要整数格也能改，但那会让松手瞬间画面跳一下。
- **按住不放期间是连续出帧的**（跟着 vsync，约 60fps），不是"来一个触摸事件才画一帧"。
  后者在真机上手感时好时坏：事件的投递节奏不均匀，画面就会一跳一跳，
  极端情况下事件被攒在一起，就变成"拖动时一直看旧画面、松手才跳过去"。
- 屏幕旋转、切到后台再回来，局面与视野都不丢；**后台时间不计入成绩**。

## 界面

```
┌───────────┬────────────────────────────────┐
│ 游戏  帮助 │                                │  菜单栏（**只在左侧栏宽度内**）
├───────────┤                                │
│   🙂 笑脸   │                                │
│  计雷器 +实 │                                │
│  计雷器 −实 │        棋盘（满高，可拖动）      │  左侧信息栏宽 = 长边/5
│  计雷器 +虚 │                                │  右侧棋盘 = 剩下 4/5，
│  计雷器 −虚 │                                │            且从窗口最上沿开始
│   计时器    │                                │
└───────────┴────────────────────────────────┘
```

- 菜单栏只占左侧栏那一条，右边那片上方空间**全部并进地图**：
  棋盘从窗口最上沿开始、满高（1920×1080 上纵向因此多出整整一条菜单栏的高度）。
- 信息栏在**左边、竖排**：最上面是笑脸，然后四块计雷器（正实 / 负实 / 正虚 / 负虚，
  虚雷第四格是 `i` 单位），最下面是计时器。
- **单格固定 0.7cm**（按屏幕密度换算成设备像素；280dpi 上 77px、440dpi 上 121px）。
  格大小不随难度变化，手指点得准。密度取
  `getResources().getDisplayMetrics().densityDpi`，所以**不同像素密度的手机上
  单格物理尺寸一致**。
- **自适应规则**（任意窗口尺寸 × 任意密度，自检覆盖 72 种组合）：
  - 侧栏宽 = 窗口长边 / 5，并钳在 `[UI_MIN_SIDE_W, win_w/2]`
  - 单格 = 0.7cm 对应的像素数（下限 1px）
  - HUD 缩放 = 能让侧栏装下的最大整数（与单格尺寸解耦）
  - 菜单栏高度 / 按钮尺寸 / 下拉行高 = **max(比例值, 按字号实测的最小值)** ——
    字号是固定像素、hud 不随密度变，所以必须按字号保底，否则高密度屏上会裁字
- **可见格数固定**：一屏只显示落格区放得下的整格数（1920×1080 上是 19×12）。
  更大的盘靠拖动看其余部分 —— 这样高难度的大图也不会一屏挤满、点错。
- HUD（菜单栏 / 笑脸 / 计雷器 / 计时器）用自己独立的**整数**缩放
  （挑能让侧栏装下的最大整数，1920×1080 上是 4×），与单格尺寸解耦。
- 菜单只有 **6 项**（新局 / 初级 / 中级 / 高级 / 自定义 / 纪录）。
  原来的 1×/2×/3× 缩放已删掉：改成"单格固定 0.7cm + 拖动"之后缩放档位不再参与布局。
- **自定义棋盘**：六个数值（高 / 宽 / 四种雷）用每行右侧的 **▲▼ 按钮**增减。
  安卓侧是 `hasCode="false"` 的 NativeActivity，**没有软键盘**，
  所以数值不能用"点输入框打字"。步进 1，并在硬边界内钳制；
  「确定」才做最终校验（不合法会显示错误提示，提示行在字段区与按钮之间）。
- **所有浮层（玩法 / 关于 / 纪录 / 自定义）的面板几何只有一个定义**
  （`overlay_geom()`），绘制、按钮、字段、命中判定全部共用它。
  面板宽高按内容实测，不写死。自检里有"每个按钮必须完整落在面板内"的断言当哨兵。
- **界面字号按屏幕密度分三层**（`tools/ui_strings.js` 的 `SIZES`）：
  基准 sm/md/lg = **21/29/39**（对应 280dpi、单格 77px），另有 125% 与 150% 两层，
  运行时按**目标单格**挑一层 —— 单格是 0.7cm 的物理常量，所以"跟单格成比例"
  就等于"跟屏幕密度成比例"，各设备上的**物理**字号因此基本一致（2.5~2.9mm）。
  字形是固定像素高度的光栅图、不能任意缩放（缩放就糊了），所以只能预生成几层。
  字号与 `src/ui.c` 顶部的 `L_*` 常量是配套的，自检里有
  "菜单文字必须完整落在按钮内"、"侧栏内容不许溢出"的断言当哨兵。
- 横屏锁定（`sensorLandscape`）：高级盘 30 格宽，竖屏下每格只有十来个物理像素，点不准。

## 规则有两份实现，靠三道闸门锁住

安卓侧的规则是 C（`src/game.c`），Windows 侧是 Zig（`正式版/src/rules.zig`）。
为什么会有两份：Zig 0.14.1 没法给 Android 链接 libc（`unable to find or provide libc
for target ... android.14`），所以「同一份源码两端共用」在规则层走不通。

重复就有飘走的风险，所以：

1. **规则自检**：`selftest.c` 移植了 `selftest.zig` 的每一组不变量，35 项断言。
2. **跨端对拍**：`tools/parity_check.js` 让两端的 `--rules-dump` 在**同样的种子、
   同样的开局格**下各跑一遍局面，逐格签名（`雷类型/显示值/状态`）逐字对比，
   共 395 个局面。这一步接在构建里，不一致就让构建失败。
3. 两个文件头都写明「改动规则时两份必须一起改」。

> 对拍会打印一句「n 个局面的 fnv 值不同」：两端的 FNV 实现细节不同，但这个哈希只是
> 冗余信息 —— **逐格签名**才是内容等价性的判据，所以门禁按签名判定。要让报告更干净，
> 把两侧 `dumpBoard` 的哈希算法改成完全一致的逐字节 FNV-1a 即可。

### APK 结构校验都查什么

`tools/check_apk.js` 逐条检查那些"装到手机上才发现"的坑：

- 没有 `classes.dex`（`hasCode=false` 的纯原生应用不该有）
- **所有 `.so` 都是 stored（未压缩）** —— Android 直接从 APK 里 mmap 这些库
- 原生库在合法的 ABI 目录下
- `minSdk ≥ 24`、`targetSdk ≥ 33`、入口是 `android.app.NativeActivity`
- 没有声明竖屏特性（专家盘需要横屏）
- `assets/atlas.bin` 与 `assets/font_atlas.bin` 都在
- 签名可校验

## 已知限制

- **默认出 `arm64-v8a` + `x86_64` 两个 ABI**（约 289 KB）。MuMu 是 x86_64，现在原生运行，
  不再依赖 ARM 转译。只想要真机包可以 `-Abis arm64-v8a` 把体积压回约 160 KB。
- 用**调试密钥**签名（`android/debug.keystore`，构建时自动生成）。自己装够用，
  要发布请换成你自己的密钥。
- **单格固定 0.7cm、可见格数固定**：一屏能显示多少格完全由屏幕尺寸决定。
  1920×1080 上是 19×12 格（1463×924 px），专家盘 30×16 要拖动才能看全。
  屏幕特别小的设备上安全钳制会把单格压到"至少能显示 6×5 格"，
  此时单格会小于 0.7cm —— 保可用性优先于保物理尺寸。
- 帧缓冲尺寸 = 窗口尺寸（没有缩放层），所以**只有软件渲染**：1920×1080 下
  每帧要重画约 200 万像素。因为只在有输入/动画时出帧（空闲 50ms 轮询），
  实际占用可以接受；但要是以后加持续动画，得先改成局部重绘。
- **CI 目前只构建 Windows 版**（`.github/workflows/build.yml`）。安卓版没有进 CI，
  因为字形流水线依赖 Windows 的 `System.Drawing`、而 `android_toolchain.ps1` 里的
  NDK/build-tools 路径与下载文件名都是 Windows 专用的。
  仓库里提交了字形生成物，所以**构建本身**不再需要跑那条流水线；
  但要在 Linux runner 上构建，仍得先把工具链探测改成跨平台
  （NDK 用 `linux-x86_64`、build-tools 用 `_linux.zip`、clang 不带 `.exe`、另配 JDK）。
- 音效仍未编进程序（与 Windows 版一致，上游一直是"试听候选"状态）。

## 排障记录

以下四条都是真机（MuMu 12，Android 12，x86_64，横屏 1920×1080）实测出来的；
它们的成因都不在"看起来最像"的地方。

### 一、触屏完全没反应

**表现**：点哪里都没反应，画面永远停在启动那一刻。

**真因**：不是输入没到，而是**应用只画了第一帧、之后从不重绘**。

排查过程（每一步都留了证据）：

1. 加诊断日志后发现输入完整到达：`action=0 pid=0 at (960,600) -> ui(504,492)`，
   按下/抬起都在，坐标映射也正确。→ 排除输入链路。
2. 连点同一格 5 次，每次 `screencap` 的 MD5 **完全一样**；按 Home 键后截图立刻变化
   （15 KB → 2 MB）。→ 画面冻在首帧，与输入无关。
3. 生命周期日志：`INIT_WINDOW → GAINED_FOCUS → LOST_FOCUS → CONTENT_RECT_CHANGED`。
   旧代码在 `APP_CMD_LOST_FOCUS` 里把 `animating` 置 false，主循环随即
   `ALooper_pollOnce(-1)` **永久阻塞**。
4. `on_input` 里虽然把 `animating` 置回 true，但 native_app_glue 是在**主线程**的
   `source->process()` 里回调它，而那一步发生在 timeout **已经取成 -1** 之后：
   内层 `while` 处理完输入立刻又调 `pollOnce(-1)` 阻塞，**永远走不到绘制代码**。
   于是"输入被处理了，但画面永不更新"——玩家看到的正是完全没反应。

**修法**：焦点不再参与"要不要画"，引入 `need_frame` 请求位；主循环超时从 `-1` 改成
有界（忙时 0、空闲 **50 ms**）。空闲每秒 20 次唤醒，开销可忽略，但保证任何输入最多
50 ms 内一定补画一帧。`need_frame` 不能进 `busy` 判定（它在循环末尾就被消费），
否则会变成 0 ms 自旋。

**回归判据**：点按同一格 5 次，5 张截图 MD5 必须互不相同，且第 5 次精确回到初始帧
（旗帜循环 1→2→3→4→0）。

### 二、四周一圈大灰框

**表现**：游戏窗口只占屏幕中间一小块（1920×1080 上只用了 504×425，约 23%）。

**真因**：布局档位与显示缩放**各自为政**。旧的 `ui_auto_zoom` 只按"整数档位的布局能否
装进窗口"挑档，平台层再用 `scale = 窗口宽 / 客户区宽` 算放大倍率，两个判据不同源、
互相抵消。更根本的是：z=3 时表头要 990z 宽，布局宽到 1512z 直接超过 1080p 的宽度使
z=3 不可用；而 z=2 的 1008×850 只能放 1 倍，竟比 z=1 放 2 倍还差。

**修法**：把"挑档"和"放大"合成一件事 —— `ui_pick_layout_and_scale()` 在所有
`(档位 z, 整数倍率 s)` 里选出**实际覆盖面积最大**且装得下窗口的那一组。放在界面层
（`ui.c`）而不是平台层，是为了能进宿主机自检（自检里用暴力枚举对拍"这确实是最优"）。

**效果**：内容从 504×425 @1× 变成 1008×850 @2×，面积翻 4 倍，屏幕覆盖 23% → 41%。

### 三、单格算成了 0.07cm（单位错误）

界面上线后第一版真机日志：

```
屏幕密度 280 dpi → 单格 8px（目标 0.1cm）
```

**真因**：0.7cm 的换算写成 `(7 × dpi + 127) / 254` —— 分子少乘了 10。
正确的整数式是 `(70 × dpi + 127) / 254`（分母 254 = 2.54cm/英寸 × 100，
分子里 0.7cm 要先放大成 70 才能对上）。

这个错的连锁反应比看起来大：格子只有 8px 时，"至少显示 6×5 格"的安全钳制
永远不触发，于是 30×16 的专家盘被一屏全塞进去 —— **"可见格数固定 + 拖动"
这套设计直接失效**，而且日志还显示"可见 30×16 格"，看起来一切正常。

**修法**：换算挪到 `ui_cell_px_for_dpi()`（界面层，能进自检），
自检里对 160/240/280/320/420/480 dpi 逐点断言像素数，并反过来校验
物理尺寸落在 0.70cm ±0.03cm 内。这样单位错误不可能再溜到真机。

### 四、拖动没反应（两处，都在拖动这条新路径上）

**表现**：`input swipe` 拖了完全没变化；日志里 `pan_active` 确实变成了 1。

**(1) 不足一格的位移被"整格吸附"归零。**
拖动中每来一个 MOVE 事件都调 `ui_pan_to`，而它当时和"落盘"共用一个
`normalize_pan`（钳制 + 吸附到整格）。只要单次位移不到一格，
`v - v % cell` 就把整个位移抹成 0 —— 而 `input swipe` 与真机轻扫的单次位移
通常都不到一格（77px）。日志里 `raw=50` 而 `pan=0` 就是这么来的。

修法：区分两个概念。拖动中用 `live_pan`（**只钳制**，保留不足一格的位移，
这样才跟手）；松手时 `ui_pan_end → ui_refresh_scale` 用 `normalize_pan`
（钳制 + 吸附到整格，静止时屏幕上必须是完整格子）。

**(2) `ui_pointer_cancel` 把 `pointer_down` 清掉了。**
拖动开始时调 `ui_pointer_cancel` 清按格手势，它顺手把 `pointer_down` 置了 false。
但 `pointer_down` 表示的是"手指还按在屏幕上"这个**物理事实**——手指并没抬起。
于是下一个 MOVE 进来时，`ui_pointer_move` 开头的 `if (!pointer_down) return;`
直接返回：**拖动只处理了第一个 MOVE 事件就死了**。

这个坑特别隐蔽：每个单步都"看起来正常"（`pan_active` 成了 1、`pan_begin`
也执行了、坐标也对），只有把整串 DOWN→MOVE×N→UP 连起来断言才抓得到。
现在自检第 19 组就是这条整串回归，并且我**故意把 bug 注回去验证过它确实会失败**
（9 条断言同时报错）。

**顺带修的**：拖动范围原来按"落格区"算，滚到最右时会露出一条棋盘外的空白。
改成按**视口**算（`origin ∈ [vis_x + view_w - board_w, vis_x]`），
自检第 20 组对两端各断言"棋盘边界必须盖满视口边界"。

### 五、拖动后右侧少画格子（你截图发现的那个）

**表现**：拖动棋盘时，右侧会空出一条灰带，而且**拖得越多空得越宽**；
拖到最右端时空出的宽度正好等于拖动量。

**真因**：绘制循环写成

```c
for (vc = 0; vc < L->vis_cols; vc++) {
    col = first_col + vc;          // 起点已经跳过了 first_col 格
    ...
}
```

`vis_cols` 是"一屏放得下几格"（19），而 `first_col` 是"从棋盘第几格开始显示"。
两者相加就把可见格数**多算了 first_col 格**，但画布只放得下 vis_cols 格，
于是右侧少画 `first_col` 格 —— 而 `first_col` 恰好等于拖动量。

修法：布局里直接算出本帧要画的格号区间 `vis_first_col .. vis_end_col`，
由"棋盘 ∩ 视口"反推（区间端点按裁剪矩形取整），绘制与命中共用同一套几何，
不再出现"起点 + 容量"这种会重复计数的写法。

**为什么自检没抓到**：原来只断言了"棋盘边界盖满视口"和"绑定同源"，
而这条 bug 恰好不违反那两条（画出来的格子确实在棋盘范围内）。
现在第 21 组直接断言**画到的格子必须盖到裁剪矩形边界**，
并在 5 个拖动位置逐一检查，这条才真正锁住。

**验证**（拖到最右端后数竖网格线，视口右边界是 1859）：

| 版本 | 竖网格线 | 最右一条 |
| --- | --- | --- |
| 修之前（你截图那次） | 15 条 | x=1402（右边空 ~450px） |
| 修之后 | 21 条 | x=1787 ✓ |

> 另外记一笔排查教训：中途我两次根据**缩放过的预览图**判断"右边空了"，
> 又两次被逐像素比对推翻，来回折腾了很久。真正定案的是一次**定量测量**
> （数竖网格线的条数和最右位置）——几何问题一律用像素测量，不要看缩放图。
>
> 这一轮还顺手修掉了两个**只在宿主机预览里出现、不影响真机**的毛病：
> 拖到最右时宿主渲染右侧少画格子（根因同上），以及 `--pan` 选项因为
> `if (pan_x >= 0 || pan_y >= 0)` 条件恒真而**从未生效**过。
> 后者一度让我误判"设备渲染与宿主完全一致"，因为比对脚本两边读到的其实是同一张图。

### 六、拖动时好时坏：有时跟手、有时只看得到旧画面

**表现**：拖动的流畅度不稳定。有时画面跟着手指走；有时拖动过程中一直显示旧画面，
**松手才一下跳到最终位置**。

**真因**：主循环是**事件驱动**的 —— 来一个 `ACTION_MOVE` 才画一帧。
系统投递触摸事件的节奏并不均匀（会合并、会抖动），于是画面按事件的节奏一跳一跳；
事件被攒在一起时（拖动较快或主线程正忙），中途就一帧都不画，直到松手。

**排除掉的可能**：先量了单帧耗时，稳定在 **16–17ms**（≈60fps），
所以不是"画得太慢"，而是"该画的时候没去画"。

**修法**：只要界面还"忙"（手指按着 / 在等双击窗口 / 脸在闪），
主循环就用 **0 超时轮询**（立刻返回、不阻塞等事件），每轮都重新出帧，
主动以显示刷新率去画。`eglSwapBuffers` 本身按 vsync 节流，所以不是空转烧 CPU；
空闲时仍退回 50ms 有界轮询省电。

**验证**：只投递 3 个 MOVE 事件、然后**按住 2 秒不投任何事件**，日志显示这 2 秒里
连续出了 120 帧（间隔 16–17ms）。也就是说"没有新事件"时画面依然在持续刷新，
以前正是这种情形会卡成静止画面。

### 七、起拖时"要拖过一段距离才进入平滑拖动"（残留的死区）

**表现**（上面那个修完之后的实测反馈）：出帧已经连续了，但**起拖的头一段依然不动**，
必须拖过一小段距离才突然开始跟手。

**真因**：不在出帧，而在**起拖门槛**。当时用 `UI_PAN_SLOP_PX = 8`：
位移不到 8px 就一帧都不平移 —— 那是一段**死区**。
8px 在 280dpi 下只有 0.73mm，听着很小，但换算成时间就很明显：

| 手指速度 | 跨过 8px 需要 |
| --- | --- |
| 50 px/s（慢慢拖） | **160 ms** |
| 100 px/s | **80 ms** |
| 200 px/s | 40 ms |

再加上系统投递的坐标本身还有几像素抖动/滞后，实际死区比 8px 更大 ——
所以每次起拖都能感知到"先卡一下，然后突然跟上"。

**修法**（三个改动，缺一不可）：

1. **阈值 8px → 2px**。同一个慢速拖动只要 40ms 就进入跟手。
2. **平移基准改成"按下点"，不再重贴**。旧代码在跨过阈值那一帧才 `ui_pan_begin`，
   于是基准之前的位移被丢掉；改成以按下点为基准后，跟手时**从按下点算起**，
   不丢像素、也不会有"突然跳一下"。
3. **"是拖动还是点按"从"起拖时判"改成"松手时判"**（`ui_pointer_settle`）。
   这样阈值只用来保护长按/点按不被手抖误判，而拖动本身可以尽早生效。

**验证**（设备上模拟真机慢速起拖，每次只挪 3px）：

| 挪动 | 最右竖网格线 |
| --- | --- |
| 3px | 1857 |
| 6px | 1856 |
| 12px | 1852 |
| 18px | 1846 |

从第 3px 就开始动，且位移与网格线移动量严格一比一（12px→−7px、18px→−11px）。
另外直接用日志核过：`down_dx=-20 → pan=20`，即**拖 20px 就走 20px**。

**连带修掉的**：长按不被手抖吃掉。手指在格子上轻轻抖 1px 时，按格手势必须保留
（否则每次长按前只要手一抖，长按就失效了）。现在"抖动"与"拖动"用同一把尺子判，
抖动时按格手势原样保留。

### 八、每把新局雷区完全一样（严重）

**表现**：点「新局」之后，如果开局点的格子和上一把是同一格，**生成的雷区一模一样**。

**真因**：安卓侧所有"新局"入口都把种子**写死成 `1`**，而 Windows 版用的是
`GetTickCount()`。因为"第一次点击必安全"的实现方式是
**先按种子铺满雷、再把开局那一格的雷挪走**，
所以只要「种子相同 + 开局格相同」，挪雷的结果就完全相同 —— 每把都是同一张图。

受影响的入口（全部写死为 1）：菜单「新局」、三个难度、自定义盘「确定」、`ui_init`。
（人脸重开当时用的是 `now | 1u`，那个是对的。）

**验证**：连做三次「新局 + 点同一格」，局面指纹完全相同：

```
第 1 次：db34ca5c
第 2 次：db34ca5c
第 3 次：db34ca5c
```

**修法**：新增 `ui_fresh_seed()`，种子 = `now_hint`（平台层每帧写入的毫秒时间）
混合一个每次调用必增的计数器；五个入口全部改用它。
混计数器的理由是**同一毫秒内连续新局也不会撞种子**（否则快速连点两下新局还是同一张图）。
若 `now_hint` 看起来不像时钟（自检里就是这种情况），就只用计数器 ——
这样"同一进程内每次新局都不同"始终成立，同时不破坏依赖固定种子的测试。

**验证（修好之后）**：连续 4 次「新局 + 点同一格」，指纹互不相同：

```
1ff804fe 7f61a287 9e306106 96511f73
```

设备上也核过：连续三把点开同一片区域，露出的数字与雷位完全不同。

**为什么自检没抓到**：所有自检都给新局**显式传了种子**（`ui_cmd_new_game(…, 12345, true)`），
于是"种子是不是新鲜"这件事从来没被检验过 —— 只测了"给定种子时规则对不对"。
现在第 23 组专门断言"连续新局的雷区必须不同"，覆盖 `CMD_NEW`、换难度、自定义盘三条路径。

> 另外记一笔教训：这条断言第一版我写成"新局后立刻取指纹"，结果三局都相同 ——
> 因为**雷区要等第一次翻开才铺**，没翻开时每局都是"空盘"，指纹恒等，
> 断言是在比较三个空盘。必须 `game_start_at` 之后再取指纹。

### 九、不同手机屏幕 / 像素密度下的自适应（两处真 bug）

这一轮的目标是"自动适配不同像素比例的手机屏幕"，体检 72 种「窗口 × 密度」组合后
发现两处**真的会坏**。

#### 9.1 屏幕密度查询一直失败 → 单格永远按 280dpi 算（严重）

**表现**：无论屏幕密度是多少，单格边长都按 280dpi 计算。真机多为 395~560dpi，
所以手机上单格会只有 **0.44cm**（该是 0.70cm），明显偏小。

**真因**：`android_main` 跑在 native 线程上，**那个线程默认没有 attach 到 JVM**。
`(*vm)->GetEnv(...)` 直接返回 `JNI_EDETACHED(-2)`，函数立刻退回兜底常量 280。

**验证**（MuMu 上用 `wm density` 覆盖，看应用日志里的单格）：

| 设定密度 | 修复前 | 修复后 |
| --- | --- | --- |
| 280 dpi | 280 dpi → 77px | 280 dpi → 77px = 0.70cm |
| 395 dpi | **280 dpi** → 77px ❌ | 395 dpi → 109px = 0.70cm ✓ |
| 440 dpi | **280 dpi** → 77px ❌ | 440 dpi → 121px = 0.70cm ✓ |

**修法**：`GetEnv` 返回 `JNI_EDETACHED` 时先 `AttachCurrentThread`（只 attach 一次，
进程存活期间不 detach）；并且密度优先取
`getResources().getDisplayMetrics().densityDpi` —— 这是"当前真正在用"的值，
能反映 `wm density` 覆盖与厂商自定义值；`getConfiguration().densityDpi` 退为兜底
（它只给桶值 160/240/320…，会把 420/440 抹平）。

#### 9.2 高密度屏上菜单中文被裁掉（严重）

**表现**：2160×1080 @440dpi 下，菜单栏的「游戏」「帮助」只露出下半截。

**真因**：字号是**固定像素**高度（md23），而 hud **只随窗口像素尺寸变化、不随屏幕密度变化**。
于是"像素多但 hud 不够大"的组合（440dpi 下仍然是 hud=4）里，
菜单栏高度与按钮宽度按 `× hud` 算出来就装不下字了：440dpi 时 hud 仍是 4，
菜单栏 36h=144px、按钮 20h=80px，而 md 文字墨水高 27px、宽 46px，加上边框与内边距就被裁掉。

**修法**：菜单栏高度、按钮宽度/高度、下拉行高全部改成
`max(比例值, 按字号实测的最小值)`，其中"最小高度"由新增的
`font_ink_height(FONT_MD)` 提供（字形表里所有字形墨水范围的总高，27px）。
这样两头都稳：hud 大时按比例，hud 小时按字号保底。

**验证**（修复后各配置都 ok）：

| 窗口 @ 密度 | hud | 菜单栏 | 需≥ | 按钮宽 | 文字宽 |
| --- | --- | --- | --- | --- | --- |
| 2160×1080 @440dpi | 4 | 144 | 27 | 86 | 46 |
| 1600×720 @320dpi | 3 | 108 | 27 | 76 | 46 |
| 1024×600 @240dpi | 2 | 72 | 27 | 66 | 46 |

设备上按像素量过：文字 y = 60..83，按钮 y = 8..136 —— 完整落在框内。

#### 9.3 自检补强

原来只断言几何（"侧栏宽度为正""可见格数为正"），**不看文字放不放得下**，
所以 9.2 那种"字被裁掉"根本抓不到。现在第 24 组遍历
**8 种窗口 × 9 种密度 = 72 种组合**，每种都断言：

- 菜单栏高度容得下 md 字号的墨水高度
- 两个菜单按钮的文字**纵向**完整落在按钮内（用 `font_text_ink_bounds` 实测）
- 两个菜单按钮的文字**横向**装得进按钮
- 侧栏、棋盘区、可见格数、hud 均为正

> 记一笔教训：我在改这块时用 PowerShell 数组拼接搬代码块，把 `ui.c` 文件顶部
> 弄坏过一次（多出孤立的大括号与残句），编译直接报 `extraneous closing brace`。
> **改动源码请用 edit 工具，不要用脚本整体重写文件**；脚本只用来做只读分析与构建。

### 十、非 1920×1080 的设备上内容只占左上角一块（严重）

**表现**（用户在另一个分辨率的 MuMu 设备上实测）：画面右侧一大片黑，
内容只占左上角一块，比例也不对。

**真因**：`ui_resize()` 早就写好了，**但平台层从来没调用过它**。
平台初始化时是 `ui_init(&app.ui, 1920, 1080)` —— 写死的默认值，旁边还有一句注释
"真正的屏幕尺寸在 `APP_CMD_INIT_WINDOW` 里拿到之后再重算"，
**而那段重算的代码从来没写**。

于是非 1920×1080 的设备上：

- 帧缓冲 = 真实窗口尺寸（`app->width/height` 来自 `ANativeWindow_getWidth`）
- 布局 = 永远按 1920×1080 算

两者对不上，内容就被画在左上角，右边/下边留黑。

**验证**（MuMu 新设备 2712×1220 @280dpi）：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 非黑内容范围 | x=0..**1919**（右侧 792 列纯黑） | x=0..**2711**（铺满） |
| 内容尺寸 | 1920×1080 | 2712×1220 |
| 侧栏宽 | 384px | **542px**（= 2712/5 ✓） |
| 可见格数 | 19×11 | **27×13** |

**修法**：在 `rebuild_framebuffer()` 里、算布局之前先 `ui_resize(&app.ui, width, height)`。
这样 `INIT_WINDOW` / `WINDOW_RESIZED` / `CONFIG_CHANGED` / `CONTENT_RECT_CHANGED`
四条路径全都会同步（它们都走这个函数），窗口尺寸从此真正驱动布局。

**多种分辨率实测**（同一台设备上用 `wm size` 覆盖，测完已 `reset` 还原）：

| 设定/实际窗口 | 内容尺寸 | HUD | 侧栏 | 可见格 |
| --- | --- | --- | --- | --- |
| 2712×1220 | 2712×1220 ✓ | 4× | 542 | 27×13 |
| 2560×1440 → 2440×1440 | 2440×1440 ✓ | 4× | 488 | 25×16 |
| 1920×1080 | 1920×1080 ✓ | 4× | 384 | 19×11 |
| 1280×720 | 1280×720 ✓ | 3× | 256 | 13×7 |

**补的回归测试**：第 25 组遍历 7 种窗口尺寸，断言
`ui_resize` 之后布局宽高等于窗口宽高、棋盘区**右边/下边贴到窗口边界**
（不是只占左上角）、侧栏 = 长边/5。

> 为什么原来抓不到？早先所有测试都是 `ui_init(&ui, w, h)` 直接给目标尺寸，
> 于是"init 之后再也不同步窗口尺寸"这条路径**从来没被走过**。
> 而设备上真实的路径是"先 init 默认值 → 再 INIT_WINDOW 同步"。
> 教训：测试要走**和真实代码一样的路径**，不要图方便直接构造终态。

### 十一、大屏上"拖动完全不平滑"（视口吃掉了拖动行程）

**表现**：在 2712×1220 的设备上，拖动完全不平滑 —— 手指挪一小段画面就不动了。

**真因**：修掉上面那个 `ui_resize` 之后才暴露的**回归**，而且是"修对了反而变差"那种：

| | 可见列 | 拖动行程 |
| --- | --- | --- |
| 修 `ui_resize` **之前**（布局错误地按 1920 算） | 19 | **847px** ← 反而够用 |
| 修 `ui_resize` **之后**（布局正确地按 2712 算） | 27 | **231px** ← 一拖到底 |

屏幕越大、能显示的列越多，**剩下的可拖行程就越少**。专家盘 30 列，屏幕能显示 27 列，
就只剩 3 列（231px ≈ 手指挪 2cm）可以拖，之后画面完全不动。

**修法**：某个轴真的超出屏幕时，把视口限制在**该轴的 3/4**，于是行程至少是棋盘的 1/4。
**只在真的超出时才限制**：棋盘本来就装得下的那一轴直接显示整盘（那种盘不需要拖，
限制反而会变成"小盘也要拖" —— 我第一版就是这么错的，9×9 被切成 6 列）。

**验证**：

| 设备 | 难度 | 可见列 | 拖动行程 |
| --- | --- | --- | --- |
| 2712×1220 | 高级 | 27 → **22** | 231 → **616px（8 格）** |
| 1920×1080 | 高级 | 19（不变） | 847px（不变） |
| 1920×1080 | 初级 9×9 | 9（整盘入屏，不用拖） | 0 |
| 1600×720 | 高级 | 14 | 1408px |

设备实测（注入 12 步、每步 50px）：

- 日志：`down_dx=-50 → pan=50`、`-300 → 300`、`-600 → 600`，**1:1 且单调**
- 逐帧比对：每一步相邻帧在棋盘区差异 **约 39%**（画面确实在动）
- 松手后与最后一步差异 **0.0%**（不跳）
- 单帧耗时 16–17ms（60fps）

**回归测试**：第 26 组覆盖 8 窗口 × 5 密度 × 3 难度 = **120 种组合**，断言
"某轴溢出时视口 ≤ 该轴的 3/4"、"有行程就必须至少能动 2 格"、"单格不低于目标"。
断言总数 897 → **1421**。

> 又一个"测试要走真实路径"的教训：这一条之所以能做出来，是因为测试会**真的跑
> 每个难度预置**，而不只是构造一个抽象布局。

> 排查教训：我一开始用自己写的"数竖网格线"脚本判断"画面有没有动"，
> 结果它给出的位移量来回跳，让我误判成"拖动在反弹"。
> 换用**逐帧差异比例**和**应用自己的 pan 日志**后结论立刻清晰。
> 自制的图像度量如果不先验证可靠性，就会变成新的误导源。

### 十二、"必须按住一小段时间后才能平滑拖动"

**表现**：手指按下后**立刻**拖动 → 一顿一顿、不平滑；
先按住一小会儿再拖 → 就平滑了。

**真因**：主循环的内层 `while` 把绘制代码**饿死**了。

```c
while (ALooper_pollOnce(timeout, NULL, &events, &source) >= 0) {
    if (source) source->process(android_app, source);   // MOVE 事件在这里被处理
}
if (!app.has_window || !app.gl_ok) continue;
...
draw_frame(&app);        // ← 绘制在这里，只有 while 退出才轮得到
```

拖动时输入队列的 fd **一直是可读的**（手指持续产生 MOVE 事件），
所以 `ALooper_pollOnce` 每次都有活干、返回 ≥ 0，**这个 while 永远不退出**，
后面的绘制一帧都轮不到。

- 立刻拖：事件流连续不断 → while 不退出 → **一帧都不画** → 一顿一顿
- 先按住：事件流出现空隙 → while 退出一次 → 画一帧 → 之后还有空隙 → 看起来平滑

**实测证据**（`input swipe` 生成真实 60Hz 事件流，2 秒滑动 600px）：

| | 修复前 | 修复后 |
| --- | --- | --- |
| PAN 事件 | 121 | 120 |
| **实际出帧** | **0** | **24** |
| 帧间隔 | —（没帧） | 16–17ms |
| pan 进度 | 走到 600 但没画 | 15→40→65→90…590 逐帧跟上 |

**修法**：每轮循环**只取一次事件**，取完就往下走去绘制，绘制完再回来取下一个。
事件变成"每帧最多处理一次"，但输入本身是排队的、不会丢；
绘制也拿到了与 vsync 对齐的稳定节奏。

```c
if (ALooper_pollOnce(timeout, NULL, &poll_events, &poll_source) >= 0) {
    source = poll_source;
}
if (source) source->process(android_app, source);
... draw_frame(&app);
```

**验证（最终版，设备上真实事件流）**：拖动中途连抓三帧，与起始帧差异
33.1% / 6.8% / 38.7%，相邻帧差异 34.9% 与 38.7% —— 说明每一段都在持续出帧。

> **这条是我自己引入的回归**。最早那版是"来一个 MOVE 才画一帧"（真有问题），
> 我把它改成"忙的时候连续出帧"（本意是对的），但用 `while` 包住 `pollOnce`
> 就变成了"事件越多越画不出来"—— 恰恰在最需要出帧的拖动场景下彻底不画。
> 教训：**主循环里"取事件"和"出帧"必须是同一层级的顺序步骤，
> 不能让取事件的循环有能力无限占用控制流。**

### 十三、浮层三个毛病：面板/按钮各算各的几何、自定义面板点不动

用户报的现象：

1. 点「玩法」「关于」后的提示框，**大小和文字不匹配**
2. 「游戏 → 自定义」的提示框**既不能改数字也不能点确定**

**真因（一个根因，两个症状）**：浮层的几何有**两份**，而且不一样。

```c
// draw_overlay 里：面板
py = (win_h - panel_h) / 2;
// overlay_buttons 里：按钮
cy = (menubar_h + win_h) / 2;      // ← 另一套公式！
```

1080 高的屏上两者差 128px。实测：

| | 面板 | 按钮 | 结论 |
| --- | --- | --- | --- |
| 玩法/关于/纪录 | y=412..668 | y=772..852 | 按钮在面板**下方 104px** |
| 自定义 | y=416..664 | y=688..728 | 确定/取消在面板**下方 24px** |

所以「玩法/关于」看起来是"面板里空了一大块、按钮跑到外面"；
而自定义面板的**确定按钮根本不在面板里，点不到**。

**第二个问题**：自定义面板的数值**本来就不能用键盘改** ——
安卓侧是 `hasCode="false"` 的 NativeActivity，**没有软键盘**，
点输入框只会把它设成"聚焦"，打不出任何字。

**修法**：

1. 新增 `overlay_geom()` 作为**唯一**的面板几何来源，
   绘制、按钮、字段、命中判定全部从它取。面板宽高改为**按内容实测**
   （正文最长一行 / 标题 / 标签 / 按钮行），不再写死 `74h × 64h`。
2. 自定义面板的六个数值改成**上下箭头按钮**增减（`UI_HIT_DLG_INC/DEC`），
   步进 1 并在硬边界内钳制（高 9..GAME_MAX_H、宽 9..GAME_MAX_W、雷 0..格数−9）。
   `ui_dlg_step()` 只改数值不做最终校验，校验仍留给「确定」。
3. 自定义面板改成 **3 行 × 2 列**（左：高/宽/正实雷，右：其余三种雷），
   高度按内容算，并在字段区与按钮行之间留一整行给错误提示。

**验证**（设备 1920×1080 @280dpi 实测）：

| 步骤 | 结果 |
| --- | --- |
| 打开 游戏→自定义 | 面板打开，六个值框 + 12 个箭头都在面板内 |
| 点「高度」加号 3 次 | 高度 16 → **19** |
| 点「正实雷」加号 2 次 | 正实雷 25 → **27** |
| 其他四项 | **不变**（宽度 30、负实雷/正虚雷/负虚雷 25/25/24） |
| 点「确定」 | 面板关闭、盘面按新尺寸重开 |
| 重新打开面板 | 预填 高 19 / 宽 30 / 正实雷 26（均分后）→ **确定确实生效了** |

**回归测试**：第 27 组覆盖 5 窗口 × 4 浮层，断言
"面板在窗口内"、"每个按钮完整在面板内"、"值框/箭头在面板内且不重叠"、
"箭头不小于 3h×3h"、"标签不压值框"、"字段不压按钮行"、"最后一行与按钮行之间放得下错误提示"；
第 28 组模拟真实指针点击 12 次箭头 + 确定 + 取消，断言数值变化与边界钳制。
断言总数 1421 → **1659**。

> 两个值得记的坑：
> 1. **一份几何只能有一个定义**。绘制和命中各写一套，早晚会分叉；
>    这次分叉的直接后果是"按钮点不到"，而且从代码上看两处都"挺合理"。
> 2. 我在算面板高度时引用了 `g.body_y`，而它要靠 `h` 才能定 ——
>    **读到未初始化内存**，面板高度变成 6 万多，箭头全跑到屏幕外，点哪都没反应。
>    教训：几何函数里只许用"已经算出来的量"，并且给结果加合理性兜底。

### 十四、字号太小、且完全不随分辨率变

**表现**（用户）："字体和提示框太小，还是说你没对字体适配分辨率？"

**真因（两个叠加的问题）**：

1. **字号是写死的像素值（sm17/md23/lg31），完全不随屏幕密度变化。**
   而单格是 0.7cm 的**物理**常量，密度越高像素越多。于是字高与单格的比值
   在不同设备上差一倍多：

   | 设备 | 单格 | 菜单字物理高 | 字高/单格 |
   | --- | --- | --- | --- |
   | 1920×1080 @280dpi | 77px | 2.45mm | 0.35 |
   | 1080p 手机 @440dpi | 121px | **1.56mm** | **0.22** |

   440dpi 手机上中文只有 1.56mm 高 —— 确实小到看不清。

2. **基准尺寸本身也偏小**：即使 280dpi 的机器上，2.45mm 也低于安卓正文
   （约 2.2~2.5mm）的观感，菜单和浮层显得单薄。

**修法**：

1. **基准字号整体调大**：sm/md/lg 从 17/23/31 → **21/29/39**。
2. **字号按密度分三层**（`tools/ui_strings.js` 的 `SIZES` + `src/font.h` 的
   `FONT_LAYER_COUNT`）：100% / 125% / 150%，运行时由 `font_layer_for_cell()`
   按**目标单格**挑一层（单格是 0.7cm 的物理常量，所以"跟单格成比例"
   就等于"跟屏幕密度成比例"）。
   字形是**固定像素高度的光栅图，不能任意缩放**（缩放就糊了、丢掉像素风），
   所以必须预生成几层、运行时挑最接近的一层。
3. 配套放大 HUD 常量：`L_PANEL_H` 32→38、`L_MENUBAR_UNIT` 36→50、
   `L_MENU_ITEM_W` 20→26；浮层按钮高度 12h→14h，**按钮宽度改为按最长文案实测**
   （"按合计均分"是 5 个汉字，字号变大后 120px 的按钮装不下 145px 的文字）。

**验证**（物理字号从差 1.6 倍收敛到 1.14 倍）：

| 设备 | 密度 | 字号层 | md 物理高 | 字高/单格 |
| --- | --- | --- | --- | --- |
| 1920×1080 | 280 | 100% | 2.90mm | 0.42 |
| 1080p | 395 | 125% | 2.64mm | 0.38 |
| 1080p | 440 | 150% | **2.83mm**（原 1.56） | 0.40 |
| 1080p | 480 | 150% | 2.59mm | 0.37 |
| 平板 | 320 | 100% | 2.54mm | 0.36 |

**连带修掉的一个回归**：字号变大后侧栏内容**溢出屏幕**（实测计时器
y=975..1135，而侧栏只到 1080）。原因是 `pick_hud_scale` 用的
`sidebar_content_h()` 高度公式**和真实排版不是同一套**（少算了间距）。
现在 `pick_hud_scale` 直接构造一个临时 Ui、调 `ui_layout()`，
用**真实的计时器矩形**判断装不装得下 —— 不再维护第二套公式。

> 这已经是**第三次**踩"两套公式各算各的"了（浮层几何、侧栏高度、还有菜单
> 按钮宽度）。结论写在这里：**同一份几何只能有一个来源**，
> 凡是"算一遍来判断、再算一遍来绘制"的地方，早晚会分叉。

> 另一个坑：三层字号最初都叫 sm/md/lg，结果覆盖率门禁报错 ——
> 生成与检查脚本是**按名字**查表的，重名会让后两层读成 0 个字形。
> 现在叫 sm0/md0/lg0、sm1/md1/lg1、sm2/md2/lg2。

### 十五、把"零头灰边"换成规范宽度的滚动条

**表现**（用户）："不常见的分辨率下，右侧和下方仍然存在灰色边框，影响观感"。

**真因**：不是外框，而是**落格区里放不下整格时剩下的零头**。
视口只显示整数格，`board_w - vis_cols*cell` 就空在那里：

| 窗口 | 落格区右侧余量 |
| --- | --- |
| 2712×1220 | **476px** |
| 2400×1080 | 226px |
| 1024×600 | 50px |

宽度是 23~476px 不等的零头，随分辨率乱变，所以"看着很脏"。

**修法**（按用户要求）：

1. **外框规范为固定 3h**（不再随格子大小变）。
2. 落格区让出**一个格子边长**的带子，在那里画**滚动条**：
   - 横条贴棋盘区下边、纵条贴棋盘区右边，**厚度严格 = 单格边长**
   - 滑块长度 ∝ 可见比例（可见格数/总格数），位置 ∝ 当前偏移/最大偏移
   - 全盘装得下时滑块铺满整条轨道（表示"没有可滚动的部分"）
3. **拖动滑块移动地图**：滑块跟手（按"手指位移"推滑块位置）；
   直接点轨道则滑块中心跳到手指处。滑块最小长度 56px（保证抓得住）。
   滚动条拖动与棋盘拖动是两套逻辑，用 `sb_drag` 区分。

### 十五之二、滚动条与棋盘之间那条灰缝（追加三轮才彻底解决）

**表现**（用户）："滚动条与游戏界面之间还是有灰框"，**换了几种分辨率都还在**。

这条缝隙其实是**三个独立问题叠在一起**，第一轮只修了最表面的一层：

**第 1 层：零头没去处。**
视口只显示整数格，`(棋盘区 − 外框×2 − 一格) % 单格` 的零头无论怎么取整都会剩下，
就落在格子与滚动条之间。1920×1080 上是 **65px**。

**第 2 层：滚动条锚错了边。**
修掉第 1 层后我把滚动条锚在**棋盘边缘**，而视口在左/上，中间又空出 55px。

**第 3 层：3/4 上限把滚动条撑成了一条大灰边。**
"视口最多占棋盘 3/4"这条规则（原本为了保证金拖动行程）让视口比落格区窄，
腾出来的空间并进滚动条后，2712 上滚动条宽达 **452px = 6 格**，看着就是一条大灰边。

**最终方案**：

1. **滚动条固定一格厚**（`sb_thick = cell`），且
   **横向条横跨视口宽度、贴在视口正下方；纵向条纵跨视口高度、贴在视口正右方**。
   - 轨道长度取"视口尺寸"是关键：滑块长度 ∝ 可见/全盘，这个比例只有在
     轨道与视口一样长时才等于"可拖行程的比例"。早先用剩余空间当轨道，
     1920 上轨道比视口还短，算出的滑块比轨道还长（拖动直接没有行程）。
2. **把"3/4 上限"换成"至少留 MIN_DRAG_CELLS = 4 格可拖行程"**：
   `max_vis = (棋盘 − 4格) / 格`，不再收窄完把空间塞给滚动条。
3. **单格 ±2px 微调**：既然要求"滚动条恰好一格厚 + 可见格必须完整"，
   就只剩"让单格变一点点"这一条路。在目标值 ±2px 内挑一个让
   `(可用 − 格) % 格` 最小的值（77→75/76，不到 3%，肉眼与手感无差别），
   零头从 65px 降到 12~18px，且留在**棋盘外边缘**而不是格子与滚动条之间。
4. **配色**：轨道用更亮的底 + 深色边（凹陷的槽），滑块用按钮面色 + 立体凸起 +
   中间两道抓握线。早先轨道填深灰、滑块用面板同色，两者糊在一起 ——
   屏幕上只剩一条深灰带子，那正是用户看到的"灰框"。

**验证**（设备 1920×1080 像素测量）：

```
格子右边界 1818  ==  纵条 x 起点 1818   ✅ 零缝
格子下边界  984  ==  横条 y 起点  984   ✅ 零缝
横条 x=393..1818（宽 1425 = 视口宽），纵条 y=159..984（高 825 = 视口高）
滑块：396..1292（宽 875 ≈ 1425×1425/2325）；纵向 162..723（长 561）
拖动后横条滑块 → 919..1815（行程 523px），画面变化 4.2%
```

**回归测试**：第 29 组覆盖 8 种窗口，断言"厚度 = 单格"、
**"横条在视口正下方、纵条在视口正右方"（即零缝）**、两条不越界、
两条**不重叠**（否则命中会把纵向按成横向）、轨道与滑块长度合法、
行程为 0 或 ≥ 4 格、拖到 3/4 处 pan 也到 3/4、拖到底 pan = 最大、松手不弹回。

> 教训：同一处"看着像"的毛病可能是**多层原因叠加**。第一轮我只看到"零头"那一层，
> 修完以为好了，用户看到的却是下一层的灰边。**每一轮都要重新量像素**，
> 而不是假设"上次那块已经修过了"。

> 另两条踩过的坑：
> - 设备上第一次测"往左拖"完全没动，我一度以为有 bug，其实滑块**起始就在最左端**，
>   往左拖算出的位置是负的、被钳到 0 —— 那是正确行为。
>   **测试方向要和控件当前位置匹配**。
> - `sb_grab` 一开始存成"按下点相对轨道的绝对偏移"，却在移动时按"手指相对按下点的位移"
>   来用 —— 两者符号相反、正好抵消，滑块纹丝不动。现在明确分开：`sb_base_x/y` 存按下点屏幕坐标。

### 十六、整个界面文字乱码（多页字形图集的页长度不一致）

**表现**（用户）："文字全是乱码"。设备上菜单栏显示成"跳过RTST""3456女釵"之类，
宿主机渲染却完全正常。

**真因**：`font_atlas.bin` 头部只记了**一个** `page_h`（= 各页最大高度），
运行时按 `page_w/8 × page_h` 算每页步长取字形。
但生成脚本给每页只分配了**该页自己用到的高度**：

| | 页 0 | 页 1 |
| --- | --- | --- |
| 实际写入 | 262272 字节（h=2049） | **76544 字节（h=598）** |
| 运行时按 page_h 期望 | 262272 | **262272** |

于是从第 1 页取字形时读起点偏了 185728 字节，读到的是别处的数据 —— 字形盒坐标
指向不存在的像素，屏幕上就是乱码。

**为什么以前没暴露**：本项目原来只有 1 页（993 个字形），那一页本身就是最高页，
长度正好相等。扩到 **9 个字号档、2277 个字形**变成 2 页之后立刻中招。

**修法**：
1. `gen_font.js` 里**所有页都补齐到统一高度**（短的补零），并加长度断言，
   不满足就直接抛错。
2. `font.c` 的 `font_init` 加运行时兜底：每页声明的字节数必须 ≥ 一整页，
   否则拒绝加载。
3. 新增 `tools/check_atlas.js` 作为**构建门禁**：检查
   magic/版本/尺寸字段与 `font_meta.h` 一致、每页长度 = stride × page_h、
   页数据总长 = 文件长度、所有字形 page 下标与包围盒合法。
   我人为把第 1 页改短后运行，它立刻报错，说明门禁有效。

**根因之外的第二个坑（同样重要）**：构建脚本原来只按 `tools/ui_strings.js` 的哈希
判断要不要重生成图集。我只改了 `gen_font.js`（排布逻辑），哈希没变 ——
**构建一直复用旧的坏图集**，所以我"改好了却测不出来"，白排查一轮。
现在 `font.stamp` 同时包含 `gen_font.js` 的哈希。

> 教训：**生成的产物的"生成器"改了，缓存必须失效**。只哈希输入数据（文案）
> 而不哈希生成逻辑，就会出现"代码对了、产物还是旧的"这种最难查的状态。

> 另外：`android/build.ps1` 的 UTF-8 BOM 这次又被 `edit` 工具弄掉了，
> 脚本立刻因为中文变乱码而报 `Missing type name after '['`。已补回 BOM，
> 并在 README 里再记一次：**改这个文件后要确认前 3 字节是 239,187,191**。

### 十七、菜单栏精简到左侧栏宽度，把上方空白并进地图

**表现**（用户）："把游戏和帮助的横栏缩短到左侧 ui 范围内，把空白的上方划到地图画面里"。

**改法**：

| | 改前 | 改后 |
| --- | --- | --- |
| 菜单栏 | 横跨窗口全宽（1920 宽） | **只在左侧栏那一条**（384 宽） |
| 棋盘区 | `y = menubar_h` .. 窗口底 | **`y = 0` .. 窗口底（满高）** |
| 侧栏 | `y = menubar_h` .. 窗口底 | 不变 |

三处必须同步改，少一处就会串位：

1. `ui_layout`：`L.board_y = 0; L.board_h = L.win_h;`
2. `draw_menubar`：底板与下沿阴影都只画到 `L->side_w`；
   按钮若超出侧栏宽度就 `break`（宁可少画一个，也不压到棋盘上）
3. `ui_hit_test`：菜单栏空白改成 `y < menubar_h && x < side_w`；
   侧栏判定加 `y >= L.side_y`（否则菜单栏那一条会被算成侧栏）

**效果**（设备 1920×1080 实测）：

```
菜单栏 384×150（只在侧栏内）   棋盘 x=384..1920  y=0..1080（满高）
可见格 18×10  →  19×12          （纵向多出 2 行，同时单格微调后宽也多 1 列）
```

**回归测试**新增：
- `棋盘满高（顶部空白并进地图）`：board_y == 0 且 board_h == win_h
- **`棋盘区里没有点被判成菜单/侧栏`**：在 x ≥ board_x 的区域按 11px 网格全扫一遍
- 原来那条"侧栏与菜单栏上的点不会被判成棋盘格"的扫描循环**必须从全宽改成侧栏宽度** ——
  菜单栏只占侧栏后，它右边**就是棋盘**，扫过去命中棋盘格是**正确**行为。
  （这条断言在改布局时直接失败了，正好说明它把旧布局写死了。）
- 单格断言从"hud 之间必须完全相等"放宽到 ±2px（微调会受外框厚度影响差 1~2px）

### 十七之二、画面下方那条灰边（滚动条没铺满）

**表现**（用户）："画面下方还有灰边，你自己 mumu 截图看看"。

**排查**：这次没有猜，而是把底部区域按 70×12 采样打成**字符矩阵**（`.`=192 面板、
`#`=128 深色、`+`=223 亮色），一眼看出结构：

```
格子到 y=909 结束 → 横条（有边框的方块）909..984 → **984..1071 纯面板色**
```

**真因**：`(棋盘区 − 外框×2 − 视口)` 再减掉一格厚度之后，总会剩下
`(可用 − 一格) % 一格` 的零头（1920 上是 **87px**）。条带只画"一格厚"，
那块零头就成了一条**什么都没画的纯面板灰边**。

**修法**：两条滚动条都**铺满到棋盘内边缘**（右下角）：
- 横条：`x` 从视口左边 → 棋盘内右边缘；`y` 从视口下边 → 棋盘内下边缘
- 纵条：`y` 从视口上边 → 棋盘内下边缘；`x` 从视口右边 → 棋盘内右边缘

滑块换算仍按**视口尺寸**当轨道长度（这才是"可拖行程的比例"），
所以条带变长不影响滑块比例。

两条在右下角**重叠**，命中按横向优先 —— 与绘制顺序（横向后画、压在上面）一致。

**验证**（设备 1920×1080 像素测量）：

```
格子右下 (1818, 909)   横条 x=393..1908  y=909..1071（铺到内边缘 1911/1071）
纵条 x=1818..1908  y=9..1071
横条：滑块 396..1292 + 槽 1295..1908
底部只剩外框本身 9px（1071..1080），与右侧外框 1911..1920 对称
拖动后滑块 396..1292 → 919..1815，画面变化 9.1%
```

> 教训：这次先**把像素打成矩阵**再动手，一次就定位了。前几轮我是"看一眼截图就猜是哪块"，
> 猜错了两轮。**当形状不明确时，先把数据铺开看结构**。

### 十七之三、滚动条又变成"两格宽"了（把轨道和滑块两层几何分开）

**表现**（用户）："下方的滚动条怎么变成两格宽了。。"

**真因**：上一轮为了消除灰边，我把滚动条**整条矩形**从"一格厚"改成了
"铺满到棋盘内边缘" —— 长度对了，但**厚度也跟着胀到 162px（2 格）**。

**修法**：把滚动条的几何**拆成两层**，这是最终稳定下来的模型：

| | 轨道（track） | 滑块（thumb） |
| --- | --- | --- |
| 长度方向 | **铺满到棋盘内边缘**（吃掉 `(可用 − 一格) % 一格` 的零头） | 按可见/全盘换算 |
| 厚度方向 | 跟着长度自然胀开 | **严格一格**（横块的高、纵块的宽） |
| 谁负责消灰边 | ✅ 轨道铺满 | — |

- `sb_*_track_rect()` → 轨道（铺满视口之外的剩余带）
- `sb_*_rect()` → 滑块（一格厚，贴在轨道靠视口/靠上那一侧）
- 命中用**轨道**矩形（槽里任何位置都点得到）

**验证**（设备 1920×1080 像素矩阵）：

```
横滑块 y=909..984（厚 75 = 一格）   横轨道 y=909..1071（铺到内边缘）
纵滑块 x=1818..1893（厚 75 = 一格） 纵轨道 x=1818..1911（铺到内边缘）
原来 988..1071 那条"什么都没画的纯面板灰边"现在是轨道底色（223）+ 深色边
```

**回归测试**新增（第 29 组）：
- `横轨道铺满到棋盘内右边缘` / `横轨道铺满到棋盘内下边缘` / `纵轨道铺满到棋盘内右下边缘`
- `横滑块厚度 = 一格` / `纵滑块厚度 = 一格`
- `轨道底部（零头处）命中横向` / `纵条上方段命中纵向`

> 教训：**"铺满"和"变厚"必须分开说**。我上一轮只想着"把那块空白填掉"，
> 就顺手把整条矩形放大了，长度对了但厚度错了。修这类几何要**逐轴问清楚**：
> 这一轴是长度还是厚度？该固定还是该伸缩？

### 十八、菜单里的中文字被切掉一半

**真因**：把一行文字在按钮里居中时用的是**行高**（22px，含给下伸部预留的空隙），
而不是**这段文字真实的墨水范围**（18px）。行高本身没错（它决定行距），但拿它居中会让
文字整体偏下，在 22px 高的按钮里直接被裁掉。

**修法**：新增 `font_text_ink_bounds()` / `font_center_y_for_text()`，按真实墨水范围居中；
并加了"文字必须完整落在按钮内"的断言。菜单按钮同时从 34z 加宽到 44z。

### 十九、内容区是个纯黑矩形（最早那一轮）

当时用 `glTexImage2D(..., GL_RGBA, ..., GL_BGRA_EXT, ...)` 想省掉通道交换，但 GLES2
规范里 `glTexImage2D` 的 format **只保证接受 `GL_RGBA`**，`GL_BGRA_EXT` 需要
`GL_EXT_texture_format_BGRA8888` 这个**可选**扩展。不支持的设备上调用报
`GL_INVALID_ENUM`、纹理没被分配、采样返回 `(0,0,0,1)`，画出来就是一个纯黑矩形。

改用 `GL_RGBA` 直接上传、**不做通道交换**：帧缓冲的内存顺序本来就是 `R,G,B,A`
（`CS_RGB(0xFF,0,0) == 0xFF0000FF`，小端下字节是 `FF 00 00 FF`）。当时我一度误判成
BGRA 并加了一次"交换"，反而把 R/B 换反 —— 是宿主机自检第 12 组断言把它抓住的。
现在 `draw_frame` 里还有 `glGetError()` 检查与一次性的 `GL_RENDERER` 日志。
